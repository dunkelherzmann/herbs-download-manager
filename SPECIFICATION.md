# Herb's Download Manager: specification

Herb's Download Manager (Herb's DM for short, where space is tight, such as the macOS menu bar) is a download manager for macOS, Linux and Windows. It downloads one file over many connections
at once, from one server or from several mirrors of the same file, and stops and resumes without losing what it has.
Its main inspiration is Progressive Downloader (threads and mirrors per task). Its window, toolbar and
icons follow AB Download Manager's layout; its menus are in one Main Menu (☰), as in Herb's Terminal. There are no tags.

The macOS version is the reference. The Linux and Windows versions look and work 1:1 like it, except the window
controls: minimize, maximize and close sit on the right, and the Main Menu (☰) takes the left corner of the title bar.

**App icon** (`icon/icon.svg`, its own design): a frosted-white drive, its lid narrower at the top, with a gray
download arrow coming in from above and a blue light on the right of its base, on a blue macOS-style rounded square
with a dark blue rim. `icon/make.sh` draws it for every platform: `macos/Resources/AppIcon.icns`,
`linux/icons/hicolor/` (PNG sizes and the SVG, named after the Flatpak id) and `windows/icons/app.ico`.

Section 12 summarizes the reference apps this design was drawn from, with sources.

## 1. Platforms and build

| Platform | App | Build |
|---|---|---|
| macOS 15+, Apple silicon | Swift 6 + AppKit host over the shared core | Built on Mac |
| Windows 11 | Rust Win32 host (`windows` crate) over the shared core, one static portable `.exe` (no installer, nothing added to the system) | Built on Windows |
| Linux | Rust GTK 4 + libadwaita host (`gtk4-rs`) over the shared core, Flatpak `org.herbsdownloadmanager.app` | Built on Linux |

- **Shared core** (`core/`, Rust, one Cargo workspace): the download engine (sources, segments, connections,
  mirrors, resume state, speed limits, queue) with no UI. Each host draws its native UI over it. The Mac host calls
  it through Swift bindings generated by UniFFI; the Windows and Linux hosts are Rust and use it directly.
- **Why Rust**: up to 32 connections per download write into one file at once, and Rust's compiler refuses data
  races and use-after-free in that code; async I/O (Tokio) keeps hundreds of connections on a few threads; Cargo
  builds the same core on all three machines; and the Windows and Linux hosts need no second language.
- **Networking** is the same on every platform: HTTP/1.1 through `hyper` (via `reqwest`), TLS through `rustls`
  with the operating system's certificate store (`rustls-platform-verifier`). Each connection is its own TCP
  connection, so 32 connections really are 32 (HTTP/2 would fold them into one). Proxies come from the system
  settings, read by a small function per platform.
- Protocols: HTTP and HTTPS.

## 2. Main window

The layout, top to bottom:

1. **Title bar**: the window controls, the title "Herb's Download Manager", the toolbar (§3), **Search** (🔍, T10)
   and, at the right end on macOS, the **Main Menu** (☰, §4). Search opens a find bar at the top right of the list,
   as in Herb's Terminal: it shows only downloads whose name, link or note contains the text as you type, and Done (Esc)
   hides it and shows every download again. Every menu is in the window, so on a wide screen no
   command needs a trip to the top of the screen.
2. **Toolbar** (§3).
3. **Sidebar** on the left, resizable by dragging its edge: the status filters (§2.1).
4. **Download list** (§2.2) to the right of the sidebar.
5. **Footer**: number of selected downloads, number of active downloads, total download speed.

Dropping links, text or `.txt`/`.html` files on the window adds every link found (§5.4); while dragging, the
window dims and shows "Drop links here". Dropped on an unfinished download in the list (the row is highlighted),
they become its mirrors instead (§7.1). The footer also shows a short note for a few seconds after a link becomes a
mirror ("Added as a mirror of “file.zip”").

## 5. Adding downloads

### 5.1 New Download window (⌘N)

| Id | Field | Behaviour |
|---|---|---|
| A1 | Link | the address; filled from the clipboard when it holds a link |
| A2 | Mirrors | one address per line: other servers that hold the same file (§7). Optional. |
| A3 | Name | taken from the server's `Content-Disposition` or the URL, editable |
| A4 | Save to | folder, with a Choose… button; defaults to the Downloads folder |
| A5 | Connections | a 1–32 picker, defaults to Settings ▸ Connections per download |
| A6 | Size | shown once the first source answers ("4.0 GB, resumable" or "size unknown, can't resume") |
| A7 | Stream: Only the sound | for a streamed video's link (`.m3u8`, `.mpd`): saves just its sound (§15); off and dimmed for any other link |

Buttons: **Cancel**, **Add** (adds the download to the queue, paused if the queue is stopped) and **Download** (the
default: starts it now). A file of that name in the list or the folder is handled as §5.6 says.

**Starting early.** Once the link proves resumable (and the file fits), it starts downloading into the folder shown,
while the window is still open, so no time is lost choosing the folder and name; the Size line adds "120 MB downloaded
already" (or "already downloaded"). It isn't in the list yet. **Download** or **Add** takes it over: it moves to the
folder and name chosen (copied to another drive if need be) and continues, or is listed as finished when it already
is. **Cancel**, closing the window, changing the link, Skip in §5.6, the link becoming a mirror, or quitting discards
what was fetched.

### 5.2 Add from Clipboard (⇧⌘V, or ⌘V in the main window)

Every link in the clipboard's text opens the Add Links window (§5.3). Pasting in the main window does the same: ⌘V
(Edit ▸ Paste) on the Mac, Ctrl+V on Linux and Windows, whenever no text field (the find bar's) has the cursor; one
that has takes the paste as usual.

### 5.3 Add Links window (several links)

A list of the links found, each with a checkbox, name, size and folder, and a filter field. Clicking a column's
header sorts the list by it, and clicking it again reverses the order, with the usual arrow in the header (hover text
"Sort by name; click again for the reverse order" where the toolkit doesn't show one itself): names and addresses A to
Z (case aside, numbers by value: "part 2" before "part 10"), sizes by bytes, smallest first (unknown sizes first).
Checkboxes, the filter and Check All / Uncheck All work on the sorted rows as before. Each link is checked as it arrives, four at a time: its
row gets the file's real name and size, a web page's row gives way to the files on it (§15), and a link that doesn't
answer as a file is unchecked and says why: "Offline (404 Not Found)", "Offline (The server didn't answer)" or
"Needs a sign-in". Ticking it again adds it all the same. The Linux and Windows lists
show Name, Size and Link. **Treat as mirrors of
one file** combines the checked links into one download with mirrors (offered when they share a file name or size).
**Only the sound of streamed videos** (offered when a checked link is a stream) saves just the sound of each checked
stream (§15); other files are added as they are. Buttons: Cancel, Add, Download. Links are added one at a time in list order, so links to the same file (the same
name, and the same size when known) become one download and its mirrors (§7.1 M5); the footer line says so ("5
links checked: 2 downloads with mirrors"), and afterwards the main window's footer sums up what was added. While the
window is open, links, text and link files dropped on it, or on the main window or the Dock icon, join the list as
more rows (several mirrors of one file at once, say); a link already listed is skipped.

### 5.4 Drag and drop

Links, text, and text-based files (§5.7) dropped on the window or the Dock icon open the Add Links window with
every link they contain.

### 5.6 A name in use

**Names every system takes.** Whatever names a file (its server, its page, the extension or the user), the name is
fitted before the file is made: characters some system refuses (`/ \ : * ? " < > |` and control characters) become
`_`, leading dots and trailing dots and spaces go, a Windows device name (`CON`, `NUL`, `COM1`…) gets `_` after it,
and a name longer than 230 bytes (room for " (2)" and the part file's suffix within every system's 255) is
shortened before its extension, which is kept. On Windows the whole path is also kept under 250 characters.

Whenever a download is added (New Download, Add Links, Import, clipboard, drop, Batch), a **different** file with
the same name, whether a download in the list (finished, or unfinished with another size) or a file in the folder, asks:

> A different “report.pdf” is already in Downloads. Skip the new link, replace the existing file (it goes to the
> Trash), or keep both, the new one as “report - kept.pdf”. The one there is 1.0 MB; the new one is 2.4 MB.

Buttons: **Keep Both** (default), **Skip**, **Replace**. Keep Both names the new download "<name> - kept.<ext>"
("report - kept.pdf", then "report - kept 2.pdf"; "README - kept" without an extension), so the original keeps its
name. Replace moves the existing file to the Trash and removes its download from the list. When more links follow,
**Do the same for the rest** answers once for all. Other links in the same batch for that file follow the choice:
mirrors of the kept or replacing download, or skipped too. A link to the same file as an unfinished download is
not a clash: it becomes its mirror (§7.1 M5).

### 5.7 Import Links (⇧⌘O)

File ▸ Import Links… chooses one or more files and opens the Add Links window with every link in them. It reads any
text-based file: with no extension, `.txt`, `.md`, `.csv`, `.json`, `.xml`, `.html`, rich text and word-processor
files (`.rtf`, `.rtfd`, `.doc`, `.docx`, `.odt`, web archives; their hyperlinks count too, not only the visible
text) and `.webloc` bookmarks. A file that isn't text (a zip, an image) has no links, and the app says so.

### 5.8 Export Links (⇧⌘E)

File ▸ Export Links… saves the selected downloads' links, or every download's when none is selected, as a text file
("Herb's DM links 2026-11-10.txt"). Each file's name comes with its link and its mirrors under it, drawn as a tree
the way `tree` draws a folder, oldest download first:

```
.
├── Big Buck Bunny.mp4
│   ├── https://a.example/bbb.mp4
│   └── https://b.example/m/bbb.mp4
└── notes.zip
    └── https://c.example/notes.zip
```

Import Links reads it back: Add Links gathers the links to each file into one download and its mirrors again.
`hdm export [ID…]` prints the same tree, and the MCP tool `export_links` returns it. It is off while the list is
empty.

### 5.5 Batch Download (⇧⌘N)

A link with a range placeholder makes a series: `https://example.com/img^(###1-100).jpg` gives `img001.jpg` …
`img100.jpg`. Ranges are decimal (`#` pads to that many digits), hexadecimal (`H` or `h` after the range) or
alphabetical (`a-z`, `AA-BZ`), and several ranges are separated by commas. A preview shows the first and last
links and the count before they go to the Add Links window.

## 6. Download window

Opens for a download from the list (double-click or ⌘O). Its title is the file name.

- **Header**: progress bar drawn as the file's segments (each segment colored by state, the gaps still to fetch
  left empty), percentage, downloaded / total, speed, time left.
- **Buttons**: Resume / Pause (one toggling button), Close. Closing the window never stops the download.
- **Tabs**:
  - **Info**: link, folder, size, resumable or not, date added, date finished, checksum.
  - **Connections**: one row per connection: source (host), byte range, downloaded, speed, state (Connecting,
    Downloading, Idle, Retrying in 5 s, Failed: reason). Buttons **+** and **−** add or remove a connection now.
  - **Mirrors**: the sources list (§7.3), with **Add Mirror…** and **Remove**.
  - **Options**: connections for this download, speed limit for this download ("Limit to [500] [KB/s ▾]", applied
    at once and remembered), checksum to verify at the end (algorithm MD5, SHA-1, SHA-256 or SHA-512, and the
    expected value; a pasted value picks its algorithm by its length). The whole file is checked before it gets its
    name; a mismatch fails the download ("The SHA-256 checksum doesn't match…") and keeps its data, so Restart fetches
    it again. A checksum set on a finished download is checked at once. Info shows the result ("SHA-256 matches
    (file.iso.sha256)").

## 7. Mirrors

A download has one or more **sources**: the link it was added with and any mirrors, all serving the same file.
Connections are spread over the working sources, so one file is fetched from several servers at once.

### 7.1 Adding mirrors

Mirrors can be added at every stage:

| Id | When | How |
|---|---|---|
| M1 | Before | the Mirrors field of the New Download window (§5.1), or "Treat as mirrors of one file" (§5.3) |
| M2 | During | Add Mirror… (⌥⌘M, context menu, Mirrors tab) on a running download: the mirror is checked at once and new or freed connections start using it without a pause |
| M3 | After | Add Mirror… on a paused, waiting, failed or finished download: the mirror is saved with the download and used when it resumes or restarts |

| M4 | Any | links dropped on an unfinished download in the list (§2) |
| M5 | Adding | a link added in any way (New Download, Add Links, clipboard, drop, Batch) that names the same file as an unfinished download (the same file name, and the same size when both are known) becomes that download's mirror instead of a second download; Download also resumes it |

Add Mirror… takes one address per line. A mirror equal to an existing source is ignored. A mirror that turns out
to be another file is checked and dropped as "Different file" (§7.2), so a wrong match never harms the download.

### 7.2 Checking a mirror

Before a mirror gets connections, a ranged request (`Range: bytes=0-0`) checks it:

- **Same file**: the total size must equal the download's size. A different size marks it "Different file" and it
  is never used. When the download's size is still unknown, the first source that reports one sets it.
- **Ranges**: a mirror that answers without range support can serve only a download that has one connection and
  starts from zero; otherwise it is marked "No resume support" and not used.
- **Validator**: each source keeps its own `Last-Modified` or `ETag` from its first answer and sends it as
  `If-Range` on every later range request. If a source's file changes, it answers with the whole file, which is
  refused, and the source is marked "File changed" and dropped. Mirrors never share validators, since each server
  has its own.
- When a checksum is set (§6), it is verified at the end over the whole file, whichever sources served it.

### 7.3 Sources list

The Mirrors tab lists every source: on/off checkbox, address, state (Checking, Working, Idle, Slow, Failed: reason,
Different file, File changed, No resume support), active connections, speed and bytes served. Unchecking a source
moves its connections to the others; checking it again makes it available. The original link can be unchecked too,
as long as one source stays on.

**Copy Link** (a button beside Add Mirror…, on right-clicking a source, and ⌘C / Ctrl+C in the list) puts the selected
source's address, the main link's or a mirror's, on the clipboard.

**Make Main Link** (a button beside Add Mirror… and Remove, and on right-clicking a mirror; hover text "Make Main Link:
the selected mirror becomes the download's link, and the link becomes a mirror. What was downloaded is kept") makes
the selected mirror the download's link; the old link goes first among its mirrors. A running download goes on
without a pause, and a stopped one keeps what it has. The download does it on its own too: when it stops (finished,
paused or failed) with its link failed (gone, behind a sign-in, another file or a web page) and a mirror that served
the file, that mirror becomes its link.

### 7.4 Spreading connections

- A download uses up to its **connections** setting in total (§9), and at most **connections per server** on any
  one host.
- A new connection goes to the working source with the fewest connections for its host; when the sources are equal,
  to the one with the best measured speed.
- A source that fails is retried after a delay (5 s, then 10, 20, 40, up to 60 s); its byte ranges go back to the
  pool for the other sources at once. After **retries** consecutive failures (§9) it is marked Failed until the
  download is restarted or the source is turned back on.
- Answers that retrying can't fix (404 Not Found, 403 Forbidden, 410 Gone and other 4xx except 408 and 429) mark
  the source Failed at once.
- A server that turns away extra connections (429 Too Many Requests, 503, or connections reset as they open) keeps
  the ones it accepted; the download stops opening more to that host and tries again one at a time after 60 s.
- A connection that is far slower than the others (under a quarter of the download's average per-connection speed
  for 15 s) gives its remaining range to a faster source; its source is marked Slow.
- The link counts no more than a mirror. At a fresh start every source is asked at once, so one that hangs or fails
  never holds up the others; the earliest in the list that answers with ranges and a size (within a moment of the
  first) is used. A server that sends no answer for 30 s counts as not answering, at the start and on every later
  request. A source that sends a web page while another sends the file (an expired link's "please sign in" page) is
  marked "Different file". One good mirror is enough: a bad link (missing, behind a login, stalling, refusing every
  connection, never answering, unreachable, or sending a web page) is marked and set aside like a bad mirror. With two or more mirrors, each source is asked its file's size when a
  download starts: a source serving another file, when two or more others agree on a different size, is marked
  "Different file", even the link, and the download starts from one that agrees. (With one mirror, the link's file
  decides.)
- A download fails only when no source is left working, and says why ("All sources failed: 404 Not Found").

## 8. Connections and segments

- **Disk space:** a download starts only when its file fits with 128 MB to spare, and while it runs the disk is looked
  at every few seconds: when less than 128 MB is free, it stops ("The disk is nearly full (96 MB free): free some
  space, then Resume"), keeping what it has, and Resume carries on. A stream is checked the same way before and
  between its pieces.

- **Dynamic segmentation**: a download starts with one connection over the whole file. When the size is known and
  ranges work, more connections open up to the limit; each new or freed connection takes the second half of the
  largest remaining range and starts at its midpoint. No range is split below 256 KiB.
- **Takeover**: a connection that receives nothing for 20 s is closed, its range goes back to the pool, and the
  connection reconnects (to the same or another source).
- **Writing**: data goes to `<name>.hdpart` next to the destination, written in place at its offset, and the file
  is renamed to its final name only once every byte is in and the checksum (if set) matches. The file is
  preallocated where the file system allows holes; on FAT32 and exFAT it grows in steps so Pause still works.
- **No range support**: one connection, no mirrors in use, and the download is marked "can't resume" (§10).

| S8 | Look for checksum files | On | fetches `<file>.sha256` (and `.sha512`, `.sha1`, `.md5`) next to the link and verifies with it |
| S9 | Show a notification when a download finishes | On | with **Open** and **Show in Finder** (Show in Folder) buttons; clicking it shows the file. Windows' balloon has no buttons: clicking it shows the file |
| S10 | Server limits | | how many servers limit connections, with **Forget** (§7.4) |
| S11 | Sign-ins | | how many are saved and how, with **Manage…** (§9.1) |
| S12 | Keep the server's date for finished files | Off | the file gets the server's `Last-Modified` date instead of the time it finished |
| S13 | Video stream quality | Highest | Highest, 2160p, 1440p, 1080p, 720p, 480p, 360p (§15) |
| S14 | Sound language | The stream's own | the stream's own, or one of 24 languages, each named in its own language (§15) |
| S15 | Subtitles | None | None, All, or one of the same 24 languages: the stream's subtitles kept in its file (§15) |
| S16 | Watch the clipboard for links | Off | links copied in other apps open Add Links (§5.3); what was copied before it was on, and copies made in this app (Copy Link), are left alone. Hover text: "Watch the clipboard: links copied in other apps open Add Links (what was copied before this was on is left alone)" |

Settings opens with ⌘, (Ctrl+, on Linux and Windows) as one window, and each change applies at once, with no OK
button. They are kept in `settings.json` in the app's data folder, the same file on every platform; a missing or
out-of-range value takes its default or the nearest allowed value. S1 offers **Choose…** and **Use Downloads**; when
the chosen folder is missing (a disk not plugged in), new downloads go to Downloads. S2 is the default of the New
Download and Add Links pickers. S3 and S6 apply to every download from its next start. S4 and S5 apply at once to
running downloads. S5 is shared by all downloads together, whatever their number of connections, and a download's
own limit (§6 Options) applies on top of it. With S7 other than Ask, the question in §5.6 isn't asked and that
answer is used. S8 arrives with checksum verification and isn't shown until then. S13, S14 and S15 apply to streams added
from then on: a stream keeps the quality and sound it was added with, so a paused one goes on with the same pieces.
`settings.json` keeps S14 as a list of language codes in order; Settings shows and sets the first, and leaves a longer
hand-written list alone until it's changed there.

### 9.1 Sign-ins (links that need a login)

- A sign-in belongs to a site (`example.com`, which covers its subdomains too) and holds a user name and password,
  the cookies its links need and a referer, for servers that only allow downloads from one of their pages. Each
  request to that site's servers sends them; a redirect to another site drops them.
- When a server answers that it wants a user name and password, the download fails with *The server asks for a user
  name and password*, and the app asks for them: **User name**, **Password** and **Remember for example.com** (on),
  with **Sign In** and **Cancel**. Signing in starts the download again. Left unremembered, the sign-in lasts until
  the app quits. A sign-in that was refused is asked for again, with its user name filled in.
- Sign-ins are kept in `sign-ins.json` in the app's data folder, never in the system's keychain, and only the user's
  account can read the file. As in Herb's Terminal, an **Administrator Password** encrypts passwords and cookies
  (AES-256-GCM, with a key derived from it with PBKDF2-HMAC-SHA256, 600,000 rounds and a random salt); only the salt,
  the round count and an encrypted check value are stored. Sites and user names stay readable.
- The first save explains this and offers **Create Administrator Password…**, **Store as Plain Text** (with a second
  confirmation) or **Not Now**. The password needs at least 8 characters and can't be recovered.
- Encrypted sign-ins are locked when the app starts. The first download that needs one asks for the Administrator
  Password, once per session.
- **Manage…** lists the sign-ins (site, user name, a hidden password, cookies and referer, and how each is stored)
  with **Add…**, **Edit…** (or a double-click), **Delete** (after a confirmation whose default is Cancel), **Unlock…**
  or **Lock**, and **Create** or **Change Administrator Password…**. Changing it encrypts every sign-in again; leaving
  the new password blank removes it, after a confirmation, and stores them as plain text. On Linux the list is a
  group in Settings itself.

### 9.2 The system's proxy

Every request goes through the proxy the system is set to use, and directly when there is none; this computer's own
servers are always reached directly. On Linux the app asks the desktop for each address (GIO, through the desktop's
portal in the Flatpak), so GNOME's settings, automatic setup scripts and the usual environment variables all count.
On the Mac and Windows the system's fixed proxy settings (and the environment variables) are followed, and when the
system uses automatic setup (an automatic setup script, PAC, or automatic discovery) the app asks the system for each
address: the Mac through CFNetwork, which runs the script as the system does (read again after five minutes),
Windows through WinHTTP (the script, or "Automatically detect settings"; when it can't be read or run, the fixed
proxy). A test copy can name its own script (`--pac URL`, only with `$HD_DATA_DIR`), so the computer's settings never
change for a test. HTTP and SOCKS proxies are both used.

## 10. Stop and resume

- **Kept awake while downloading:** while any download runs, the computer doesn't go to sleep on its own (the
  display still turns off as set): an activity that holds off idle sleep on the Mac, a request to the desktop not to
  suspend on Linux (through its portal, in the Flatpak), and `SetThreadExecutionState` on Windows. When nothing is
  downloading, it sleeps as usual. Closing a laptop's lid or choosing Sleep still sleeps it.

- **Pause** stops a download's connections and keeps every downloaded byte. The resume state (sources, validators,
  remaining ranges) is saved with each pause, every 5 seconds while downloading, and on quit.
- **Resume** reconnects to the working sources and fetches only the remaining ranges. It works after quitting the
  app, a crash, a restart or a power loss: at launch, downloads that were running come back Paused, with their
  ranges checked against the `.hdpart` file.
- **Can't resume**: when no source supports ranges, Pause asks "This download can't be resumed and will start over.
  Pause anyway?" with Cancel as the default.
- **A changed file**: a resumed range is checked against the server's validator (`ETag` or `Last-Modified`); on a
  server that gives none, the range starts 32 KB early and those bytes are compared with what was saved. A
  difference fails the source with *File changed on the server*.
- **Expired link**: adding a working mirror (§7.1 M3) to a failed or paused download replaces the dead source and
  continues from where it stopped.
- **Restart** discards the downloaded data (after confirming, Cancel the default) and starts again from all sources.
- **Quit** while downloads run asks "Downloads are running. Pause them and quit?" (Cancel the default) on every
  platform; quitting pauses them, and they resume at the next launch if they were running.
- **Delete** asks whether to remove only the list entry (the default) or to move the file to the Trash as well (the
  Recycle Bin on Windows), so it can be put back; nothing is ever erased. A file that can't go to the Trash (a drive
  without one) stays where it is, and the footer says so.

## 11. Queue

One queue holds downloads that were added but not started. **Start Queue** starts waiting downloads in the order they
were added while fewer than "Downloads at once" are running (every running download counts); **Stop Queue** stops
starting new ones and lets running ones finish. A download started with Download (§5.1) or Resume runs at once,
whatever the queue's limit. While the queue runs, a download added with Add starts as soon as there is room. **Stop
All** stops the queue too, so pausing everything doesn't start the next waiting download. Whether the queue runs is
remembered: a queue running at quit runs again at the next launch. The footer shows "Queue running" or "Queue
stopped" with the number of waiting downloads, the scheduler's next start or stop, and what happens when the queue
is done ("Queue running, 2 waiting, stops at 07:00, then sleeps").

### 11.1 Scheduler

Settings has a Scheduler group:

| Id | Setting | Default |
|---|---|---|
| Q1 | Start the queue at (a time, local) | Off, 01:00 |
| Q2 | Stop the queue at | Off, 07:00 |
| Q3 | On (Mon … Sun) | every day |
| Q4 | When the queue is done | Do nothing; Quit, Sleep or Shut down |

- At the start time, on a chosen day, the queue starts (Start Queue). At the stop time it stops, and downloads still
  running pause and go back to waiting in the queue, so the next start carries on with them. A stop time no later
  than the start time is the next morning's; with no start time, the stop happens on the chosen days.
- The times are checked every second. A time missed while the app was closed or the computer slept counts when the
  app next looks, and only the latest one: after a start and a stop were both missed, the queue stays stopped.
  Changing the schedule counts from then on, so a time already past today doesn't fire.
- The queue is done when it was running, had something to do, and has nothing left running or waiting (a failed
  download doesn't hold it up). Then, with Q4 other than Do nothing, the main window shows "The queue is done" with
  a 60-second countdown ("Your Mac will shut down in 60 seconds."), **Cancel** (the default) and **Quit Now**,
  **Sleep Now** or **Shut Down Now**; when the countdown ends, that happens. Stopping the queue isn't being done.
- Sleep and Shut down: on the Mac `pmset sleepnow` and loginwindow's Shut Down (macOS may ask once to allow it); on
  Linux systemd-logind (`Suspend`, `PowerOff`; the Flatpak may talk to `org.freedesktop.login1`); on Windows
  `SetSuspendState` and `shutdown /s`. A test copy (`HD_DATA_DIR` set) only logs them.
- Kept in `settings.json` under `schedule`, and when it last looked in `queue.json`.

## 12. Command line and MCP server

`hdm` controls the running app from a terminal, a script or an AI assistant. Each app ships it: inside the Mac app
(`/Applications/Herb's Download Manager.app/Contents/MacOS/hdm`), beside the Windows `.exe` (`hdm.exe`), and in the
Linux Flatpak (`flatpak run --command=hdm org.herbsdownloadmanager.app`).

| Command | What it does |
|---|---|
| `hdm list [--filter all\|downloading\|paused\|finished\|unfinished] [--search TEXT] [--json]` | id, status, size, name and note; `--json` gives every field |
| `hdm add LINK… [--folder FOLDER] [--queue] [--quality Q] [--sound LANGUAGE] [--sound-only] [--subtitles LANGUAGE|all|none] [--from H:MM:SS] [--to H:MM:SS]` | adds http and https links through the add flow (§5): links to one file become one download with mirrors; a name already in use is kept under a new name, never replaced. Starts them, or with `--queue` leaves them waiting. The folder is S1 unless given. For a stream, `--quality` (`highest`, or lines such as `1080`) and `--sound` (a language code such as `de`) choose instead of S13 and S14, `--subtitles` keeps a language's subtitles (or `all`, or `none`) instead of S15, `--sound-only` saves just its sound (§15; a link that isn't a stream is refused), and `--from`/`--to` download only a section of it (§15); the MCP tool `add_downloads` takes `quality`, `sound`, `subtitles`, `sound_only`, `from` and `to` the same way |
| `hdm pause ID…` · `hdm resume ID…` | as Pause and Resume |
| `hdm remove ID… [--delete-files]` | takes downloads off the list; with `--delete-files` their files go to the Trash (Recycle Bin) |
| `hdm note ID TEXT…` | sets the note (§4.1); empty text removes it |
| `hdm export [ID…]` | prints those downloads (all without IDs) as a tree of names with their links and mirrors (§5.8) |
| `hdm mcp` | an MCP server on standard input and output with the same commands as tools: `list_downloads`, `add_downloads`, `pause_downloads`, `resume_downloads`, `remove_downloads` (marked destructive) and `set_note` |

While the app runs it listens on 127.0.0.1 only, at a port it picks, and writes the port and a random token to
`control.json` in its data folder, readable only by the user; a request without the token is refused, and quitting
removes the file. When the app isn't open, `hdm` says "Herb's Download Manager isn't running. Open it, then try
again." (exit code 1; 2 for a mistyped command). `$HD_DATA_DIR` points `hdm` at a test copy.

## 13. Browser extension

An extension for Chrome, Edge, Brave, Vivaldi and Firefox (`extension/` in the repository) hands the browser's
downloads to the app. The browser keeps a download the app doesn't take.

- Each new download in a normal window is paused while the app checks its link, with the browser's cookies for it
  and the page it came from. If the link works for the app, the browser's download is cancelled and erased from its
  list, and the app downloads it (S1, started now). Otherwise the browser resumes it, and the extension's button
  shows "!" with the reason in its hover text for 15 seconds: the app isn't running, isn't set up for this browser,
  or the server refused it.
- Private (incognito) windows' downloads stay in the browser.
- **Straight to the app.** In Chrome and Edge, the browser's own downloads panel stays hidden while Take downloads
  is on (`downloads.setUiOptions`), so a download the app takes never opens it. It shows again while the browser
  keeps a download (the app isn't running, a private window, a page's own `blob:` or `data:` file) until that
  download ends, and whenever Take downloads is off. Firefox has no such setting and still shows its panel briefly.
- **Take downloads** is changed only by its switch: the switch sends its own state (on or off), never "the other
  one", and the setting is kept in the browser's storage, so reloading a tab, the list or the browser never changes
  it.
- Right-clicking a link, picture, video or sound offers **Download Now with Herb's Download Manager** (started at
  once) and **Add to Queue in Herb's Download Manager**. Right-clicking a page whose tab played media also offers
  **Herb's Download Manager: media on this page**, listing them (up to 20, in the list's order, as "name · kind ·
  quality"), each with **Download Now** and **Add to Queue**, as the list's buttons. Choosing one of these is a
  request for the app: when it isn't open, `hdm` opens it in the background, minimized and without taking the focus
  (`--background`), then hands it the link, started or queued as chosen.
- **Naming Rules** (the list's **Naming Rules…** button, or the extension's options page) sets, per site, how its
  videos and sounds are named and saved and what a click in the list does. A rule's site covers its subdomains, and
  the most particular rule wins (video.example.com over example.com). Each rule has: **Name**, a pattern with
  `%title` (the page's title), `%site` (the site's name without www or its ending: `youtube`, `bbc` for bbc.co.uk)
  and `%selector` (the text of the first page element its **Selector** finds, read when the item is added); its
  **Replace** pairs (`find => with`, one a line, applied in order, plain text); **Longest name** (characters, before
  the extension); a **Sub-folder** inside the folder S1 saves to (`hdm` makes it, and its `..` parts are left out so
  it can't leave that folder); and **A click in the list**: Download (add it to the queue), Ask for a name first (a
  field under the item with the rule's name, to change, then Add), Sound only (streams; files are added as they
  are), or Copy the address. The right-click menu follows the action too (Ask adds under the rule's name). The
  name is made fit for a file (characters files can't hold become spaces, spaces gathered, no leading dots,
  "no-name" when nothing is left) and gets the item's extension: `.mp4` for a stream, else the file's own. Without a
  rule nothing changes: a stream is named after its page's title, a file after its link. The page shows each rule's
  result on an example page, and saves as you type.
- **Alt+Shift+H** (Control+Shift+H on the Mac) opens the list; the browser's extension shortcuts page can change it.
- **Open in the side panel** (Chrome and Edge, under the first switch) opens the list in the browser's side panel
  instead of a popup when the toolbar button is clicked; there it follows the window's active tab.
- When the app isn't running, an item the list can't add says "Herb's Download Manager isn't running." with an
  **Open and Download** button: `hdm` opens the app (from beside itself, apart from the browser so it stays open
  when the browser closes), waits up to 30 seconds for it to answer, and the item is added and started at once
  ("Downloading"). Find Files on This Page offers **Open and Look Again** the same way.
- The toolbar button (its icon drawn without the app icon's margin, so it's as big as other extensions' buttons)
  opens the extension's list: **Take downloads** at the top (a switch: when off, the browser keeps its downloads and
  the button's badge says "off"), the media the tab played (§15) and the files found on the page, each as a card,
  and a bar of tools at the bottom: **Naming Rules** (⚙) and the extension's version ("Version 1.25") on the left;
  **Select All**, **Delete All**, **Reload**, **Find Files on This Page** (🔍), the list's **order** and **Open in
  the side panel** on the right. The list looks like the app (its colors, system blue, monochrome line icons, light
  and dark), laid out as Video DownloadHelper's.
  - **Select All** (⌘A, Ctrl+A outside a text field) ticks every item's checkbox (each card has one over its
    picture's corner) and then reads **Select None**. While any are ticked, a bar above the tools says how many
    ("3 selected") with **Add to Queue** and **Download**, which add each ticked item as its own Download would (its
    site's rule still names it; one that asks for a name or copies its address is downloaded as it is).
  - **Delete All** takes every item off the list: what the tab played, the videos in the page's data and the files
    found on the page. They stay off while the tab shows the page (a scan doesn't list them again) until Reload or
    another page.
  - **Reload** (⌘R, Ctrl+R in the list) loads the tab again, starting the list afresh (deleted items come back), and
    once the page has loaded, looks through it again (Find Files on This Page).
- **The page's own download button.** On every page and frame, a small button with the app's icon shows in the top
  right corner of the file under the pointer, and goes 0.8 s after the pointer leaves. Files are: a link to a file
  (its address ends in a file type the page scan knows, §15, such as `.zip`, `.pdf`, `.dmg`, `.mp4` or `.m3u8`, or
  the link has `download`), a picture (from 48 × 48 pixels), a picture drawn as an element's background (not the
  page's own), a video or sound (players' layers over a video don't hide it), and an embedded document (`<embed>`,
  `<object>`). A link to a file wins over what it holds, so a thumbnail that links to its full picture gives that
  picture; the button sits in the corner of the bigger of the two, and beside a link too small to hold it. Its hover
  text says "Download this file (video, sound, picture) with Herb's Download Manager". A click downloads that file at
  once, opening the app in the background when it isn't running, as the right-click menu does; the page doesn't see
  the click. A file with its own address is handed over as it is (a picture or another file keeps its own name; a
  video or sound follows its site's naming rule, which applies to videos, sounds and streams only). A video played
  through a `blob:` address is matched against what the tab fetched, as §15 says; with nothing to match the button
  turns red with "Nothing to download yet: play it first." The button turns green with a ✓ for 2 seconds when the
  app took it, red with "!" and the reason for 5 seconds when not. It sits in its own closed shadow root, so the
  page's styles can't change it.
- A download the extension hands over is asked for as the browser asked: its User-Agent, the page as Referer (when
  the browser saw a player fetch it, exactly that request's Referer, Origin and User-Agent, none when it sent none,
  and the rest of its lines (Accept, Accept-Language, Sec-Fetch-*, Sec-Ch-Ua*, its own tokens; not its cookies,
  which go apart, nor Host, Range or lengths), which servers behind Cloudflare check on a stream's pieces: a
  player embedded from another site sends its frame's address or nothing, and its server refuses any other; kept an
  hour, and with the listed item so the extension's background script going to sleep doesn't lose them; an empty
  Referer replaces one the app remembered for the site; for a stream whose own address the browser didn't see
  asked, the last headers the tab sent to its host), and otherwise
  the page's Origin when the request goes to another site (as a web player's fetches do), with every request of
  that download (a stream's playlists, keys and pieces too). Guarded streams refuse pieces to a downloader that
  introduces itself otherwise (403). When a stream is still refused, its failure says why if its links tell: a
  token that expired ("The stream's link expired at 15:26: open its page again and add it anew") or one tied to the
  browser's network address.
- **Links tied to an address family.** Sites tie a stream's links to the address of the browser that asked for them,
  sometimes its IPv6 network for one link and its IPv4 address for the next. A link that names the viewer's address
  (a token's `ip` or `ip_cidr`, or a public address written in its path or query) is fetched over that family. A
  request refused (403) over one family, from a host that has the other, is asked once more over the other, and the
  family that works is remembered for that host. This holds for a stream's playlists and pieces, and for every
  request of a file download.
- The cookies and page arrive as a sign-in for the link's site for this session only (§9.1): they're never written
  to disk, and they keep a saved sign-in's user name and password.
- The extension talks to `hdm` (§12) by native messaging, which passes on only `add` and `ping`. At each launch the
  app registers `hdm` with the browsers it finds for the user: a host manifest named
  `org.herbsdownloadmanager.hdm.json` in each browser's `NativeMessagingHosts` folder on the Mac and Linux (Firefox's
  `native-messaging-hosts`), or in the registry under `HKCU\Software\…\NativeMessagingHosts` on Windows. The Linux
  Flatpak points them at a small script that runs its `hdm` through `flatpak run`. A browser installed later is
  found at the next launch; a test copy registers nothing.
- Settings ▸ Browser extension ▸ **Show Extension Folder** writes the extension to `Browser Extension` in the app's
  data folder and shows it, with how to load it: Chrome, Edge, Brave and Vivaldi load it unpacked (Extensions ▸
  Developer mode ▸ Load Unpacked), with the id `clhikpnhhffblbcgfcpebhiholmchidg` that its manifest's key fixes;
  Firefox loads it as a temporary add-on (about:debugging), until it's signed by Mozilla.
- Firefox from a Snap (Ubuntu's) starts `hdm` through the desktop's portal, which asks once whether to allow it.
- Not yet: Safari, which only keeps extensions signed by an Apple developer; browsers in a Flatpak sandbox, which
  can't start `hdm`.

### Progressive Downloader 10.0.1 (macOS), the main inspiration

- **Tasks have threads and mirrors.** The task context menu has *Threads* (the live connections, with control

  faster servers at download start and warns that a mirror may serve malicious files.
- Threads: initial and maximum thread count per task, automatic thread count control, a warning against too many
  threads for one task, per-segment status ("Segment size … Speed …"), a *New Thread* command, and warnings when a
  task can't be resumed after Stop or Quit.
- Main window: sidebar filters Running, Suspended, Complete, Incomplete, and Schedules (Waiting, Complete), plus
  Groups and Tags; columns Progress, Size, Speed, Elapsed, Est. Time, Start, Finish, Threads, Priority, Hostname.
- Menus: File (Add Task, Import/Export Links, Open, Open in Finder), View (Visible Columns, Filters, Customize
  Toolbar), Task (Start, Stop, Restart, Remove, Remove with Data, Remove Complete, Priority ⌘1–⌘5, New Thread,
  Mirrors, Rename), Start All / Stop All, Link Box ⌘D, File Browser, History.
- Task properties: General (source, destination, maximum threads, priority, action on adding: enqueue, suspend,

  per-host connection limits; error control (retries, retry interval, idle disconnect, reconnect when speed drops);
  checksum verification; command line `-add url … destination …`; AppleScript.
- Also has torrents, video sites, FTP/SFTP/WebDAV browser and a phone companion (out of scope here).
- A reputable secondary review (Softpedia) gives the default thread count as 3.

### AB Download Manager 1.11.4 (Windows, macOS, Linux, Android), the UI model

Sources: source code (github.com/amir1376/ab-download-manager, Apache-2.0); official site abdownloadmanager.com.

- Window: menu bar merged into the left of the title bar, search at the right; sidebar with status filters All,
  Finished, Unfinished, each expanding into file-type categories, and a Queues section; resizable split; footer with
  selection count, active downloads and total speed; drop links or files on the window to import them.
- Menu bar: File (New Download, Import from Clipboard, Batch Download, Exit), Tasks (Start Queue, Stop Queue, Stop
  All, Delete ▸ All Missing Files / All Finished / All Unfinished / Entire List), Tools (Browser Integration,
  Per-host Settings, Settings), Help.
- Toolbar: Add URL, then Resume, Pause | Start Queue, Stop Queue, Queues | Stop All | Delete | Settings.
- Context menu: Open, Open With, Open Folder, Resume, Pause | Delete, Restart | Move to Queue, Move to Category |
  Copy ▸ | Edit, File Checksum, Properties.
- Columns: Name, Status, Size, Speed, Time Left, Date Added (default sort), Date Started, Date Finished, Location.

  Folder / FolderFinished / FolderUnfinished, file types, Speed, Clock).

### XDM, Xtreme Download Manager (Windows, macOS, Linux)

Sources: source code (github.com/subhra74/xdm, GPL-3.0; behaviour studied, nothing copied).

- Multi-connection segmented downloads, resume after network drops, crashes or power loss, refresh of expired links
  without starting over, browser integration, HLS/DASH video grabber, batch and clipboard lists, scheduler and queues,
  HTTP/SOCKS proxies, antivirus scan.
- Resume validation sends the first answer's `Last-Modified` as `If-Range`, deliberately not the ETag, because each
  mirror has its own ETag. A range request answered with the whole file marks the server as having no range support.
  Herb's Download Manager keeps a validator per source instead (§7.2).
- Segment stealing: a finished segment's connection takes the second half of the largest remaining range (minimum
  256 KiB); a silent segment is taken over after the read timeout; the last small piece of a range is raced on a
  second connection; on FAT32/exFAT the part file grows in steps so Pause stays responsive.
- Checksum auto-detection looks for `file.sha256` / `.sha512` / `.sha1` / `.md5` sidecars, then the folder's
  `SHA256SUMS`.

## 15. Streamed video and sound

Sites stream video as HLS (an `.m3u8` playlist of pieces) or DASH (an `.mpd` manifest). The app downloads the
pieces and joins them into one `.mp4` file with its own code in the shared core, never re-encoding anything: each
picture and sound sample keeps the bytes the site sent, so the file has the site's quality.

- **HLS:** a master playlist's quality is chosen by S13, or for that stream in the extension's list or `hdm add
  --quality`: the best one (the most pixels, then H.264 or H.265 over VP9 or AV1, then the most bits a second; every
  player opens H.264 and H.265, while QuickTime doesn't play VP9 in an MP4) whose picture is at most that many lines
  (its shorter side, so a tall phone video's 720p is 720 wide), or the smallest when every one is bigger; Highest
  takes the best. HDR versions (`VIDEO-RANGE` PQ or HLG) are left out when a standard version exists, since most
  screens show them washed out; a stream that gives no picture sizes takes its best. Its separate sound track, when
  it has one, is the first language of S14 (or the one chosen for it) that its group has, `en` matching `en-US`;
  else the group's default, the stream's own sound. Pieces may be MPEG-TS (`.ts`), MP4 fragments
  with an init section, or packed audio (bare AAC or MP3 frames behind an ID3 tag giving their time, as YouTube's
  sound comes); byte ranges, AES-128 encryption and discontinuities are handled. Protected streams
  (SAMPLE-AES, FairPlay, Widevine and other DRM) are refused with "This stream is protected (DRM): it can't be
  saved", never broken.
- **Subtitles (S15):** a stream keeps the subtitles S15 asks for (or `hdm add --subtitles`, MCP `subtitles`) as
  subtitle tracks in its MP4 (`tx3g`, which QuickTime, VLC, IINA and ffmpeg's mov_text read), each labelled with its
  language (ISO 639-2, `eng`, `deu`), alternatives to each other and off until a player turns one on. The picture and
  sound are untouched. HLS: the variant's SUBTITLES group, WebVTT pieces, one track per language, forced subtitles
  (signs only) left out; X-TIMESTAMP-MAP places cues on the picture's clock, and cues without it count from the
  stream's start. DASH: WebVTT kept as one file per language (subtitles inside MP4 pieces aren't read yet). Cues
  lose WebVTT's markup and styling; overlapping ones show on separate lines. A language whose subtitles can't be read
  is left out without failing the video; live recordings and sound only keep none.
- **A stream's mirrors:** a stream download tries its link first, then each mirror in turn, until one gives the
  stream; its pieces all come from that one source (each source cuts its own), so a mirror takes over the whole
  stream rather than sharing it. The Mirrors tab shows each one's state, the one that served it becomes the link
  (as for files, §7.3), and Make Main Link works for streams too.
- **A section of a long video:** the extension's **Download Section…** (under ▾, HLS streams) asks **From** and
  **To** (hours, minutes and seconds; To filled in with its length, From with 0:00:00) and downloads only the pieces
  that cover that part, joined into one MP4 as a whole stream is, never re-encoded: the file starts and ends on the
  stream's piece boundaries, so it's a few seconds wider than asked at most. It's named after the part:
  "Rain (1h02m00s–1h10m00s).mp4". Without To, it runs to the end. `hdm add --from --to` does the same. A section
  past the stream's end fails saying how long the stream is ("The section starts after the stream ends (12h01m01s
  long)"); live streams and DASH manifests refuse a section for now, and a whole video file isn't split.
- **Sound only:** a stream added with Only the sound (New Download A7, Add Links, the extension's **Sound Only**,
  `hdm add --sound-only`) downloads just its sound track and saves it as it came, never re-encoded: AAC as an `.m4a`
  file (MP4 with no picture), MP3 as an `.mp3` file (its frames one after the other). The name ends in `.m4a` from
  the start and becomes `.mp3` when the sound turns out to be MP3. A separate sound track (HLS's chosen as above, or
  DASH's best) is the only playlist fetched; when the sound is inside the picture's pieces, a sound-only variant is
  taken if the master lists one (its codecs name no picture), else the chosen quality's pieces, whose picture is
  left out of the file. A stream with no sound fails with "This stream has no sound to save"; Dolby (AC-3) sound,
  which can't be kept on its own here, fails saying so. A whole video file isn't split: sound only is for streams.
- **In the list:** a link whose address ends in `.m3u8` (added in any way: New Download, Add Links, `hdm add`, the
  browser extension) becomes a stream download, named after the playlist as `.mp4`: its own name, or the folder
  it's in when the playlist has a generic one (`index`, `master`, `playlist`, `chunklist`…), else the site's name.
  Its pieces download several at once (up to 6, within "Connections per download"), within the speed limits, each
  retried like a source (S6), into `<name>.hdparts` beside the file. The size shown is estimated from the pieces so
  far. Pause keeps the pieces already in, and Resume fetches only the rest; once every piece is in, the file is
  joined (Finishing) and the folder goes. Delete with its file sends the folder to the Trash too.
- **Live streams** (a playlist with no end) are recorded: the playlist is read again about once a piece's length,
  and new pieces are added as they come. A live stream that ends finishes like any other; **Pause** ends the
  recording and saves what was recorded.
- **Joining:** MPEG-TS pieces with H.264 or H.265 video and AAC or MP3 sound become an MP4 with the same samples;
  MP4 fragments are copied sample by sample, keeping their init section's edit lists (the sound's start against the
  picture), and each fragment starts at its own stated time (a sample before it lasts until then, so durations
  rounded by the stream don't add up to a drift). Packed audio is placed by its ID3 time, on the same clock as the
  picture. The index (`moov`) goes first, so the file plays before it's read to the end. A piece whose
  timestamps start again is placed right after the previous one. Kept pieces are noted with the version of each
  track they belong to (its quality's codecs, size and rate; its sound's name), and a track's pieces are set aside
  when a resumed stream's chosen version differs, never joined with another's. A codec MP4 isn't given here (AC-3 sound) leaves
  the pieces joined as one `.ts` file instead.
- **Held to ffmpeg's standard:** the core's tests join streams of each kind and compare the result with ffmpeg's own
  join (`-c copy`): every decoded picture and sound block the same, at the same times (within a millisecond), sound
  and picture as far apart as before. ffmpeg is only the tests' reference; the app never uses it. macOS doesn't
  decode MP3 sound inside MP4 (ffmpeg's file behaves the same); other players do.
- **The list's order:** a menu beside "Played on this page" (kept for next time): **Smart order** (the default)
  lists DASH videos, then HLS streams, then video files, then sounds; within those a finished stream before a live
  one (a playlist with no end), then media from the page's own site (the last two parts of its host, so
  video.example.com counts for www.example.com) before other sites', then in the order found. **Oldest first** and
  **Newest first** go by when each was found. With nothing found yet, the list says "Start the video (and skip any
  ads), and it shows here, or press Reload" (Reload, §13, loads the page again so its player fetches its media
  again); whatever the tab finds while the list is open joins it.
- **The browser extension's list:** the extension notes what each tab loads that can be downloaded, in the order
  seen: stream playlists (HLS by an `.m3u8` address or an `mpegurl` type; DASH by `.mpd` or `dash+xml`) and whole
  video and sound files (by a `video/` or `audio/` type, or a media file's extension with no type). Left out:
  stream pieces (`.ts`, `.m4s`, `video/mp2t`…), ranges and files under 1 MB that a page's script fetched (pieces
  of a player's stream), sounds under 64 KB a page plays (clicks, chimes), scripts, styles and pages. On a page
  that plays a DASH stream, video and sound files under 20 MB are left out too (its pieces), those seen before the
  manifest included. A file is named by its Content-Disposition (`filename*=` first, then `filename=`) when the
  server gives one, and counts as media by that name when its link says nothing (`/dl?id=7` sent as
  `Talk.mp3`). An address that only hints at a stream (`/api/playlist/master/`, `hls` as a part of its path, `m3u8`
  in its query) is read once to see whether it is one, at most 20 a page. A playlist is read again as its page asked
  for it: with the headers the page sent (kept 10 minutes), Referer, Origin and User-Agent set by a browser rule for
  that one address and removed after. A master
  playlist is read once and its quality and sound playlists are left out of the list. The button shows how many
  items the tab has; the list is forgotten when the tab goes to another page. Each item is a card: its preview on
  the left, then a badge for its kind (HLS, DASH, MP4, MP3, PDF…) before its name (a stream: the page's title; two
  lines at most), a line with what it is ("Video stream", "Video", "Sound"), its size and site, or how adding it
  went ("Added to the queue", "Downloading", or why not), and at the bottom right its tools: **✏** (name it first:
  a field with the name it would get, to change, then Download), what it is as a chip (format and quality or size),
  and **Download** with **▾** beside it. Download starts it at once in the app, with the page's cookies and address,
  or does what its site's rule says (§13: ask for a name first, sound only, or Copy Address); ▾ opens **Add to
  Queue**, **Download Now** (when the rule does something else), **Sound Only** (streams) and **Copy Address**. A
  stream with more than one quality or sound track shows them as chips instead: **Auto quality** (as in Settings),
  **Highest** and each picture size with its bit rate ("720p · 2.8 Mb/s", one per size, HDR left out as above); and
  **Auto sound**, **The stream's own sound** and each sound track by name and language ("English (en)"). What they
  show is what the app downloads.
Each video and stream shows a **preview** to its left, so several found on one page can be told apart: one picture
with a play mark and its length over its corner ("0:13"); a sound or another file shows its kind's mark instead. A stream's is made by `hdm` itself (the app needn't run), with the page's
cookies: the first whole picture of its smallest quality's first piece, as a tiny MP4 (a few KB), and its length from
the playlist or manifest (none for a live stream). Three are made at a time and kept while the browser runs. A whole
video file's picture and length are read by the browser, which asks for it as its page would (the site's cookies
and the page as Referer, set by a browser rule for that address for two minutes: TikTok's server refuses its files to
anyone without its `tt_chain_token` cookie). A video that can't be previewed (a DASH quality kept as one
file with no index, a protected or broken stream) keeps an empty box; sounds have none.
Each item has a **×** in its corner that removes it from the list. It stays out while the tab shows that page, even
when the page fetches it again; a video read from the page's own data is noted by its manifest. Another page in the
tab starts a fresh list.
**The page's own download button** (§13) finds the file a video plays through a `blob:` address (sites that fetch
the next videos before they're shown and play them through one, as TikTok and reels do) by its length (within half a
second; the closest wins) and picture size, against each file the tab fetched, read from its index in its first
512 KB with the page's cookies; then the video in the page's data closest to it in length (within 1.5 s); then the
tab's stream that the list shows first. A file whose link has no file's name in it is listed under its page's title, as the app
names it.
**Download** starts an item at once and says "Downloading"; **Add to Queue** (under ▾) lets it wait its turn. **Sound
Only** (under ▾, streams) adds just its sound (see Sound only above). A stream is named after
  its page ("<title>.mp4"), whatever its address; a file after its link, or its page when the link's name has no
  media extension. A file a player fetches in pieces by byte range in its address (`bytestart`, `byteend`,
  `range`) is never listed (one such piece was a reel's fragments without its beginning or sound). When the list
  opens, the extension also reads the page's scripts for DASH manifests in its data (JSON strings holding `<MPD`,
  as Facebook's reels) and lists each once, first, as "Video with sound · 720p · 2:07" under the page's title; a
  click hands the manifest to the app. Manifests a page receives later in its data replies (Instagram's and
  Facebook's feeds load each reel's `video_dash_manifest` through GraphQL as you scroll) are listed the same way: a
  small script in the page's own world (`content-main.js`) reads each XMLHttpRequest text reply, and each fetch reply
  typed JSON or JavaScript under 20 MB (from a copy), that mentions "MPD", and passes the manifests on; the extension
  keeps the newest 30 (4 MB at most) for the tab until it shows another page. The page sees no difference.
- **Scanning a page:** a web page's address typed in New Download (its size line says "A web page: Download lists
  the files and media on it", and Download or Add opens Add Links for it), or pasted, dropped or imported into Add
  Links, is read and its row gives way to the files and media found on it, each checked already: its name, size and
  kind ("78.7 KB, Video", "300 KB, Document", "Video stream"). A page with nothing on it stays as an unchecked row
  saying "Web page: no files found". `hdm scan PAGE [--json] [--add]`, the MCP tool `scan_page` and the extension's
  **Find Files on This Page** do the same. A link that is itself a file or a stream (a playlist, even one whose
  address names no type) is listed as that one item.
  - **From the browser:** the extension's list looks through the page as soon as it opens (and in the side panel,
    whenever its tab shows another page), so nothing has to be played first; **Find Files on This Page** looks again.
    Every kind of file it can download is listed (videos, streams, sounds, pictures, archives, documents,
    programs, and anything else a server sends as a file). The results' heading, "Files on this page", has **At
    least**, the smallest file to show: Any size (the default), 100 KB, 1 MB, 10 MB, 50 MB, 100 MB, 500 MB or 1 GB,
    kept for next time; files of that size or bigger show, a file of unknown size always shows, and with all left
    out the list says "No files of 1 MB or more on this page."
    It hands the app the page as the browser shows it, after its scripts ran: every frame (embedded players
    included), each with the browser's cookies for it, the addresses the frames already fetched, and the browser's
    User-Agent. The app checks what they name with those cookies, the browser's User-Agent and the frame as referer.
    Typed into the app, a page is read with the sign-ins saved for its site and a browser's User-Agent (sites send
    other programs a bare page without its player).
  - **Embedded players:** frames and players the page embeds (`<iframe>`, `<frame>`, `<embed>`, `<object>`, JSON-LD's
    `embedUrl`) and a page that only sends its visitor on (`<meta http-equiv="refresh">`) are read too, two levels
    deep, at most 12 pages in all, each with the page that embeds it as referer.
  - What's looked at: the page's links and sources (`href`, `src`, `data-src`, `srcset`, `content`, `poster`…),
    full addresses anywhere in its scripts and data, quoted paths ending in a known file type (`"clip/
    index.m3u8"`, as players write them), and addresses a player's setup names as its media by key (`"file":`,
    `"src":`, `"hls":`, `"video_url":`, `"contentUrl":`…), whatever their address looks like (up to 60 on a page).
    Addresses hidden in the text are decoded first: JSON and script escapes (`https:\/\/`, `\u002F`, `\x2F`), HTML
    entities (`&#47;`), percent-encoding (`https%3A%2F%2F`, also twice), base64, and scripts packed with the common
    `eval(function(p,a,c,k,e,d)…)` packer (its word table is read; nothing is run). Nothing a site does to keep
    downloaders out is got round: no captchas, waiting pages, sign-in forms, coded addresses or DRM.
  - What's left out before asking: pages (`.html`, `.php`…), the site's own scripts, styles, fonts and icons
    (`.js`, `.css`, `.svg`, `.woff`…), stream pieces (`.ts`, `.m4s`), and links with no file name that don't look
    like a download path (`/download/…`, `?file=…`).
  - Each candidate is checked with its server (up to 400 on a page, 8 at once, 4 to one server): it's listed when
    its type is a file's (video, sound, picture, document, archive, program, any type sent as an attachment, or
    anything over 2 MB that isn't text), or it is an HLS playlist or DASH manifest (read to be sure), at
    least 50 KB for pictures (smaller are icons and thumbnails) and 10 KB for others. Broken links and protected
    streams aren't listed. A master playlist hides its quality playlists; the page's one stream is named after the
    page ("<title>.mp4"), several after their playlists. A file whose address gives a name without a type gets its
    type's extension ("77" sent as `video/mp4` is "77.mp4"). The same name and size under two addresses is listed once.
- **DASH:** a link ending in `.mpd`, or a manifest the browser extension finds in a page's data (Facebook carries
  its reels' manifests in the page instead of loading them), is a stream download: the best video (the most
  pixels, then the most bits a second) and the best sound, joined into one MP4 like HLS (S13 and S14 choose among HLS qualities and sound tracks only, for now). Pieces are found three
  ways: one file per quality with its init section and index (`SegmentBase`, Facebook's reels: the index's
  subsegments are the pieces, fetched by byte range), listed (`SegmentList`), or from a pattern (`SegmentTemplate`
  with `$Number$` or `$Time$`, by piece length or a `SegmentTimeline`). Sound keeps its place against the picture as
  the source has it (ffmpeg's join of two separate files starts each at zero instead). Protected tracks
  (`ContentProtection`) are refused; live DASH (`type="dynamic"`) isn't recorded yet. A manifest from a page is
  kept as `manifests/<sha256>.mpd` in the data folder and downloaded from there.
